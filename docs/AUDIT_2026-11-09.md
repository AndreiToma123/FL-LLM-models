# Code and safety audit before the official runs (2026-11-09)

This audit covers the coding tasks of the execution plan (roadmap section 15): the code audit (A1-A6), the
safety-measure audit, the run protocol, and the smoke test. No GPU was used. All numbers come from the files
named in each section; the scripts that produce them are in `scripts/final/`.

## 1. Does the judge ask every pair in both orders? (A1) - YES

- **Code:** `fl_tools/selection/judges.py`, `_pairwise`: for every pair (i, j) of the shortlist it sends two
  questions, `pairwise(i, j)` and `pairwise(j, i)`. A method wins only if both answers agree; otherwise the pair is a
  draw. This holds for S5, S5+S2, S8a and S8a+S2 (S8a/S8a+S2 inherit it).
- **New test:** `tests/test_final_audit.py::test_every_pair_is_sent_in_both_orders` runs the judge against the mock
  server and reads the questions the server received: 4 tied methods -> 6 pairs -> 12 questions, each pair once as
  A-B and once as B-A, and the method outside the tied group is never asked about.
- **Saved results:** `scripts/final/judge_order_check.py` reads every per-bug `result.json` of every replay folder
  and checks `calls + cached_calls == 2 x pairs` (S5, S8a) or `>= 2 x pairs` (the +S2 variants add log-prob
  questions) and `pairs == n(n-1)/2`.

**Result: no judge run has to be repeated because of the order rule.**

## 2. What "one model call" means, and the cost per bug (A2)

**One model call = one question sent to the model.** A pair judged in both orders is 2 calls; a log-probability
score question is 1 call. Judge calls include answers taken from the cache, because a fresh run would ask them.
Front-end calls are averaged over the bugs with output (`per_bug.csv`, `llm_calls`), judge calls over all bugs.

| Pipeline | dataset 1: front end / judge / total | dataset 2: front end / judge / total |
|---|---|---|
| SoapFL + judge (S8a+S2) | 11.4 / 7.3 / 18.7 | 11.3 / 7.5 / 18.8 |
| class widening always + judge | 31.4 / 17.9 / 49.3 | 33.2 / 21.5 / 54.7 |
| class widening gated + judge | 19.9 / 13.2 / 33.1 | 26.6 / 16.4 / 43.0 |

Tokens per bug: 28.3k / 77.1k / 49.2k (dataset 1) and 23.4k / 71.1k / 56.3k (dataset 2), averaged over the bugs
with output. (The proposal's 26.5k / 22.5k for SoapFL are averaged over all attempted bugs, from `summary.md`; both
are right, the table must say which.) Source: `python scripts/final/analyze.py cost <runs>`.

## 7. Safety-measure audit

| Job type | per-bug time limit | stuck-bug guard | circuit breaker | known failures skipped on resume | how checked |
|---|---|---|---|---|---|
| SoapFL (`csc/submit.sh`) | ON, 1 h (`run_job.sbatch` passes `--timeout 3600`) | ON, 3 x the 95th-percentile time, at least 10 min, once all bugs started and at least 10 finished | ON, stops when more than 50% of at least 30 finished attempts failed (`no_failing_test_output` not counted) | ON (`--retry-failed` is never passed by default) | code + `tests/test_runner.py` (fake slow bug, fake failing set) + new `tests/test_final_audit.py` (CLI defaults, `submit.sh` dry run) |
| class widening always / gated | same (same runner) | same | same | same | same |
| new datasets (GHRB, GitBug-Java) | same runner once a bug source exists | same | same | same | not built yet (section 9) |
| judge replay (`csc/submit_select.sh`) | no per-bug limit; **NEW:** each question gives up after 120 s (was 600 s) with 2 retries, then that run's replay stops with an error (answers so far stay cached) | not needed (answers are 1-2 tokens; a replay of a whole run took 2-7 min) | a failing question stops the replay (no silent failures) | cache: a re-submitted job asks nothing twice | code + `tests/test_final_audit.py::test_select_call_timeout_option` |
| any job | Slurm time limit: front end 4 h, judge **now 2 h** (was 4 h); 5-10 min before it the job saves and stops itself | | | | `csc/*.sbatch` |

Two limits of the guards to know: (1) the stuck-bug guard needs at least 10 finished bugs and the circuit breaker
30, so in a 5-bug smoke test only the 1-h per-bug limit and the Slurm time limit protect the budget; (2) **transient
errors** (server unreachable, rate limit, killed for memory) were retried once inside a run. The run protocol says
"no reruns", so the new `--rep` option sets `--retries 0` (see section 8). A crashed model server then makes every
bug fail, and the circuit breaker stops the run.

## 8. Run protocol: 3 runs per setting, no reruns

`csc/submit.sh ... --rep R` (R = 1, 2, 3): the run name gets `-r<R>`, SoapFL seed = R - 1, `--retries 0`, and
`--retry-failed` is refused. Example for one dataset (9 front-end jobs):

    for r in 1 2 3; do
      bash csc/submit.sh qwen25coder --n all --rep $r
      bash csc/submit.sh qwen25coder --n all --classaug --ca-mode always --rep $r
      bash csc/submit.sh qwen25coder --n all --classaug --ca-mode gated --rep $r
    done
    # then the judge on each run's own lists:
    bash csc/submit_select.sh qwen25coder runall-qwen25coder-csc-r1,runall-qwen25coder-ca3-csc-r1,runall-qwen25coder-ca3g-csc-r1   # and r2, r3

**Important for the meaning of "3 runs":** the model answers greedily (temperature 0), and the seed only changes
which failing tests SoapFL reads when a bug has more than 5 (at most 45 of the 816 exported bugs, 5.5%). So the 3
runs measure mostly the run-to-run noise of the GPU server, not different "draws" of the model. That is still a
fair reliability check (it shows which differences survive repetition), but it should be described as such in the
thesis. Getting real variety would need a temperature above 0, which changes the method; that is a decision for the
user, not for the coder.

**BU estimate per dataset** (from the job notes: SoapFL 54-84, always 110-115, gated 86-92, judge 6-12 per run):
dataset 1 about 290 BU per round of 3 settings + about 25 BU of judge = about 315 per round, about 950 for 3
rounds; dataset 2 about 275 per round, about 825 for 3 rounds. Both Defects4J datasets: about 1,800 BU (plus the
smoke test, 130-250). With 2,499 used, the total would be about 4,500, under the 6,000 stop line.

The tables: `python scripts/final/analyze.py tables --dataset d4j14 --reps 3` (and `--dataset d4j2new`) writes one
Markdown file per dataset: Top-1/3/5 for run 1-3 with median and range, bugs without output per run, cost, McNemar on
the median run of each pipeline against the median SoapFL run (one main comparison per RQ, the others Holm-
corrected; "runs with a gain" = in how many of the 3 run pairs the pipeline gained more bugs than it lost), and how
many bugs flip between runs. `--reps 0` reproduces today's single-run numbers (checked: 130 / 152 / 134 / 172 / 124
/ 158 Top-1 on dataset 1). The choice of the main comparison per RQ (RQ1 = always vs SoapFL, RQ2 = gated vs SoapFL,
RQ3 = SoapFL + judge vs SoapFL) is a proposal and needs the user's confirmation.
